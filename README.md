# Автоматизация процесса «Оформление заказа»

Учебный (pet) проект по системному анализу. Полный цикл — от интервью с «заказчиком» до
готовой спецификации API и модели БД — для вымышленной компании оптовой торговли
стройматериалами «ТоргОпт», которая хочет автоматизировать приём и обработку заказов.

Цель проекта — отработать основные артефакты работы системного аналитика на одном
сквозном кейсе, вместо разрозненных учебных примеров.

## Контекст задачи

Компания принимает заказы через звонки/WhatsApp/email, менеджеры ведут учёт в личных
Excel-файлах, склад — в бумажной тетради. Из-за этого теряются и дублируются заказы,
менеджеры не видят, что клиента уже обслуживает коллега, а остатки на складе не совпадают
с реальностью. Задача — спроектировать систему, которая наводит порядок в этом процессе.

## Как читать проект

Документы пронумерованы в порядке, в котором они создавались, и в котором их стоит
читать — каждый следующий опирается на предыдущий:

1. **AS-IS** показывает, что не так с текущим процессом (раздел Pain Points)
2. **Vision & Scope** переводит эти проблемы в требования и расставляет приоритеты
   (Must/Should/Could) — не всё вошло в первую версию
3. **TO-BE** показывает, как процесс меняется с системой — какие шаги (например, звонки
   на склад) исчезают благодаря автоматизации
4. **User Story / Use Case** — детализация того, что конкретно должна делать система,
   с учётом edge-case'ов (гонка при создании записи, конфликт статусов и т.д.)
5. **ER-модель** и **API** — техническая реализация требований

## Ограничения и осознанные допущения

- Диаграмма последовательности «Синхронизация остатков с 1С» — **гипотетический**
  сценарий, не согласованный с «заказчиком»; в согласованном Vision & Scope учёт
  остатков решён без интеграции с 1С (см. раздел про отказ от штрихкодов)
- Клиент не имеет прямого доступа к системе — подтверждение заказа фиксируется
  менеджером со слов клиента (телефон/переписка), поэтому «Клиент» не входит в состав
  актёров на UML Use Case диаграмме
- Авторизация в API описана на уровне ролей (Bearer JWT + claim `role`), без детализации
  до конкретного протокола — эта часть не обсуждалась с «заказчиком» и добавлена как
  необходимый минимум для полноты технической спецификации
